# 2026.240.1921 — chore: un-land the unit verb so it can be reviewed

## Summary

Removes the `unit` verb from `main`, leaving the scaffold. **The identical code comes back in the
next PR**, where the validator reviews it as an addition.

## Why

`opencharly/plugin-unit` was an **empty repository** — no branches at all:

```
$ gh api repos/opencharly/plugin-unit/branches --jq '[.[].name]'
[]
```

There was no base branch to open a pull request against, so the initial commit created `main`
directly. That matches how the other candy repos bootstrapped (`plugin-user`'s first commit is its
whole scaffold), but the consequence here is specific and worth undoing: **~890 lines of a new
provision verb reached `main` without the pr-validator ever seeing them.**

An empty repo makes the *first* commit unavoidable-direct. It does not make the *contents*
unreviewable — it only means review has to come as a second step.

## Nothing depends on it

- no tags, no releases on this repo;
- no candy references `@github.com/opencharly/plugin-unit` anywhere in the org;
- the verb is not in any `compiled_plugins:` list.

So removing it breaks nothing, and re-adding it in the next PR is a pure addition.

## Why not just rewrite `main`

Pointing `main` at a scaffold commit would have been one step instead of two. It is deliberately not
what happened:

- **R6 forbids force-push**, and "the ref is only ten minutes old" is not an exception the rulebook
  offers — it is exactly the reasoning that erodes the rule.
- A force-push would **erase** the bypass rather than record it. Two ordered commits leave an honest
  history: the bootstrap happened, and it was corrected.

## How tested

This deletes code, so it is not a documentation change and is not claimed as one.

**The removed code's own gates, run against it immediately before removal** — it travels intact to
the follow-up PR, so this is the state being re-landed:

```
$ go test -count=1 ./
ok      github.com/opencharly/plugin-unit/candy/plugin-unit     0.003s
$ golangci-lint run
0 issues.
```

**The tree after removal** — nothing references the verb, and there is no module left to build:

```
$ git grep -n "plugin-unit/candy" -- ':!README.md'
(none)

$ find . -name go.mod -not -path "*/.git/*" | wc -l
0
```

The scaffold that remains — README plus the three org workflow dispatchers — is what every candy
repo starts from.

## Rulebook compliance

- **R0** — `/charly-internals:plugin` and `/charly-internals:git-workflow` loaded before acting.
- **R1** — the bypass was root-caused (empty repo → no base branch) rather than repeated.
- **R2** — corrected now, in this tree, not deferred.
- **R4** — no workaround: review is restored rather than the gap being documented and kept.
- **R5** — the verb is removed completely; the follow-up re-adds it as new.
- **R6** — no force-push, no history rewrite, no hook bypass. That constraint is the reason this is
  two PRs rather than one ref update.
- **R7** — the removed code was exercised (suite + lint) before removal, and the resulting tree was
  swept; both pasted above.
- **R8/R9/R10** — N/A — a deletion with no runtime path, no emitted artifact and no binary. After it
  the repo contains no Go module at all.

## Change classification

- **Class:** code/config removal — repository hygiene, restoring reviewability.
- **Verification gate:** the removed code's suite and lint green immediately before removal, plus a
  post-removal sweep showing no surviving reference and no module left to build.
- **Attribution tier:** `analysed on a live system`. The first revision claimed
  `documentation reviewed`; that was wrong and the validator was right to block it — A3 forbids that
  tier the moment code or config is touched, and a deletion of `plugin.go`, `schema/unit.cue` and
  `go.mod` plainly is. There is no fresh-rebuild R10 to run for a removal with no runtime path and no
  consumers, so the tier stops below `fully tested and validated`.
